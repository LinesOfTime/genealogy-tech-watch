## Упрощённый порядок для пользователя

Пришлите ссылки или описание находок. Codex проверяет первоисточники, существование репозиториев, новизну и лицензии, сохраняет доказательства и готовит один пакет с кратким списком изменений и оговорок. Пользователь утверждает пакет одним сообщением либо указывает исключения. Хеши, review-поля, команды apply, синхронизацию и тесты выполняет Codex после решения пользователя. Передавать пользователю заполнение JSON или ввод хешей не требуется.

До этого решения находки остаются pending. Общее поручение исследовать находки не заменяет утверждение конкретного пакета. При изменении содержания после утверждения требуется повторный просмотр затронутой находки.

## Поля записи

Обязательны discovery_id (уникальный идентификатор события), repo_full_name,
canonical_url, detected_at (ISO timestamp с часовым поясом), event_date (ISO date),
event_type, source_urls (массив объектов type/url), change_summary, previous_state,
new_state, significance_reason, components, maturity, license, license_evidence,
claims_vs_verified, risks, decision, decision_reason, review_status.
Неизвестные maturity/license указываются явно текстом «Не установлено»;
license_evidence и risks могут быть пустыми массивами. Утверждения авторов и
результаты проверки описываются в claims_vs_verified без повышения доказательности.
Для новых проектов previous_state может быть «Отсутствует в каталоге».

aliases — массив явных старых имён/URL; при непустом массиве обязателен
alias_evidence — непустой массив HTTPS-ссылок, обосновывающих перенос/алиас.
Один только общий фрагмент названия не создаёт совпадение.

Типы источников: release, commit, PR, README, ADR, paper, benchmark.
Контролируемые компоненты: Research Workspace, Archive Adapter, OCR/HTR, Indexer,
Person Resolver, Place Resolver/АТД, provenance/evidence, GEDCOM/data model,
API/MCP/agent layer.
Значимые типы событий: new_project, release, architecture, api, benchmark, license,
capability. Иные события не допускаются к публикации. Тип сам по себе не доказывает
значимость: её и дельту проверяет человек по первоисточникам.

decision: publish / research_only / watch / reject.
review_status: pending / approved / rejected. Начальное значение — pending;
reviewer и reviewed_at можно оставить null до проверки.

## Ручное утверждение

1. Проверить конкретные первоисточники, дату, дельту и значимость. Проверить алиасы,
   лицензию, ограничения и различие авторских заявлений/независимых испытаний.
2. Дополнить запись, запустить review, устранить ошибки и дубли.
3. После человеческого решения указать reviewer, reviewed_at с часовым поясом,
   review_status=approved и reviewed_content_hash, равный content_hash из отчёта.
4. Снова запустить review: eligible_for_apply показывает готовность к будущему apply.

Хеш включает все поля, кроме четырёх review-полей. Правка доказательств, алиасов,
решения или содержания отменяет прежнее утверждение. Хеш не является цифровой
подписью и не удостоверяет личность проверяющего. Инструмент не утверждает записи
сам и не проверяет содержание URL. Конкретная HTTPS-ссылка — структурный порог,
подлинность источника остаётся предметом ручной проверки.

## Сравнение и ограничения

Отчёт вычисляет catalog_match, research_matches, previous_digest_matches,
novelty_status, eligible_for_apply, content_hash, errors. Эти вычисленные поля
не нужно сохранять в исходную запись. Сравнение ведётся с каталогом по URL,
research по repo-key, дайджестом по repo и предыдущими строками журнала.
Учитываются регистр, www.github.com, завершающий слеш, .git и явные алиасы.
Несколько совпавших карточек каталога блокируют применение как конфликт.
Повтор того же источника или точной дельты одного проекта блокируется
консервативно; новая дельта с новым источником остаётся отдельным событием.
Строки журнала следует хранить в порядке обнаружения: первая занимает событие,
последующие повторы помечаются duplicate. Новые записи не заменяют прошлые.

Это не семантическая дедупликация: пересказ старого события с другим URL может
потребовать ручного отклонения. Один источник с несколькими дельтами требует
ручного объединения события. Пустое сравнение не меняет каталог или дайджест.
