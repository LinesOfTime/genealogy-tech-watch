# Watch Updater v1

Updater принимает проверяемый пакет из GitHub и передаёт его существующим
`discoveries.compare`, `apply_changes.build_plan`, `data/discoveries.jsonl`
и валидаторам. Ветка пакета служит входом, а итоговые записи и доказательства
попадают в обычный журнал, каталог, исследования и дайджест.

## Автоматический режим: «Обнови сайт»

1. ChatGPT или исследователь проверяет релиз, лицензию и отличие от уже опубликованного каталога; сохраняет проверяемые снимки первоисточников с URL, временем проверки и SHA-256 точных байтов.
2. GitHub-коннектор создаёт ветку `watch-inbox/<краткое-имя>` от `main` и записывает `watch-package.json`. Любой push в `watch-inbox/*` является триггером workflow `Watch Updater`.
3. Автоматическая задача `automatic` делает preview и сохраняет artifact `watch-preview`. При успешной валидации она рассчитывает `approval_hash`, применяет пакет и пытается отправить коммит в `main` с помощью секрета окружения `watch-publish`.
4. После выполнения необходимо проверить статус Actions, новый коммит `main` и фактическое обновление GitHub Pages. Ошибка или блокировка окружения останавливает процесс; сам факт push в inbox не равен публикации.

**Модель доверия:** в автоматическом режиме нет отдельного ручного редакционного утверждения между preview и publish. Он подходит только для предварительно проверенных пакетов; машинная валидация не подтверждает истинность внешних заявлений. Не размещайте секреты в пакете. Проверка ограничений окружения и успешной публикации обязательна до заявления «сайт обновлён».

## Ручной режим для диагностики

Откройте **Actions → Watch Updater → Run workflow** на ветке `main`. Для `preview` укажите `package_commit` (SHA коммита с `watch-package.json`), скачайте artifact `watch-preview` и проверьте diff и `approval_hash`. Для ручного `publish` укажите тот же SHA и хеш утверждения. Изменение `main` между просмотром и публикацией требует нового preview. Ручной режим сохраняет возможность явного контроля редактора.

## Формат

Один UTF-8 JSON-файл до 1 МиБ. Корневой объект имеет ровно четыре поля:

| Поле | Значение |
| --- | --- |
| `version` | Число `1`. |
| `edition_date` | Дата дайджеста в формате `YYYY-MM-DD`. |
| `events` | 1–5 событий, каждое для отдельного репозитория. Формат полей совпадает с `data/discoveries.jsonl`, статус только `pending`, решение `publish` или `research_only`. |
| `evidence` | 1–32 элемента. Ключ — путь `data/evidence/updater/<пакет>/<источник>.json`, значение — полный текст JSON снимка. Набор путей точно совпадает с `source_checks[].evidence_file`. |

У каждого снимка есть `url`, `checked_at` с часовым поясом, `http_status`
со значением `200` и `content` с полученным текстом. SHA-256 считается
по UTF-8 байтам **значения** `evidence[путь]`, включая заключительный
перевод строки, если он есть. В событии укажите типы первоисточников,
границы проверки и раздельно факты, заявления автора и независимые испытания.
Записи об утверждении (`reviewer`, `reviewed_at`, `reviewed_content_hash`)
добавляет запуск `publish`. `new_project` создаёт только новую карточку.
Для существующей карточки используйте содержательное обновление истории.
Поле `preliminary_priority` доступно новому проекту с проверенным
`catalog_profile`; допустимы P1, P2 и P3.

## Переоценка практического приоритета

Для уже существующего проекта **каждое событие в пакете Watch Updater обязано** содержать объект `priority_review`, даже если приоритет остаётся прежним:

```json
{
  "previous": "P2",
  "proposed": "P1",
  "reason": "Подтверждённые источниками основания для изменения оценки",
  "next_action": "Конкретная проверка или пилот для следующего пересмотра"
}
```

Значения `previous` и `proposed`: `P1`, `P2`, `P3`, `Не оценён`. Проверка требует ровно одной существующей карточки и совпадения `previous` с текущим `practical_priority` (либо `priority`, если практической оценки нет). После утверждённого применения обновляется `practical_priority`, а предыдущее значение, обоснование, следующее действие и ссылки на источники сохраняются в `practical_priority_history`. Если приоритет не изменился, укажите одинаковые `previous` и `proposed` и объясните почему. Пакет с обновлением существующего проекта без `priority_review` отклоняется. Это требование относится к Watch Updater, а не к историческим событиям в журнале. Это механизм фиксации обоснованного редакционного решения, не автоматическая оценка качества ИИ.

## Очередь плановой переоценки

Для проектов без новых событий предусмотрен отдельный **неизменяющий данные** отчёт:

```bash
python tools/priority_review_queue.py --date 2026-11-08 --max-age 90 --output priority-review-queue.json
python -m unittest discover -s tests -p 'test_priority_review_queue.py' -v
```

Отчёт выделяет проекты с меткой `Не оценён`, без даты документированной переоценки и с переоценкой старше заданного срока. Он использует `practical_priority_history[].reviewed_at` либо `practical_priority_reviewed_at`. Если дата отсутствует, проект попадает в очередь независимо от текущего P1–P3: это **отсутствие подтверждённой даты**, а не доказательство устаревания оценки. Отчёт не обращается к GitHub за новыми сведениями, не меняет приоритет и не запускает Actions по расписанию. Результаты требуют проверки источников и редакционного решения.

## Еженедельная очередь в GitHub Actions

Workflow [Priority Review Queue](.github/workflows/priority-review-queue.yml) запускается по понедельникам в 06:15 UTC (09:15 МСК) и через `workflow_dispatch`. Он запускает тесты `test_priority_review_queue.py`, формирует JSON и загружает артефакт `priority-review-queue` на 30 дней; краткая статистика выводится в Job Summary. Доступ только на чтение, изменений каталога и коммитов нет. После первого запуска следует проверить статус workflow и содержимое артефакта: наличие файла в репозитории само по себе не доказывает успешный запуск.

## Условия первого реального запуска

- Workflow должен находиться в `main`, а GitHub Actions должны быть
  доступны репозиторию. Есть триггеры `push` для веток `watch-inbox/*` и `workflow_dispatch` для ручного режима.
- Для ручного `preview` секреты не нужны. Для автоматической задачи и ручного `publish` настройте GitHub Environment
  `watch-publish`: разрешите только ветку `main`, при наличии настройки
  назначьте требуемых ревьюеров. Поместите туда секрет `WATCH_PUBLISH_TOKEN`
  с минимальным доступом **Contents: read/write** только к этому репозиторию.
  Владелец токена должен иметь право обычного push в `main` и право запуска
  Pages для этой ветки. Существующие правила защиты ветки действуют.
  Штатный `GITHUB_TOKEN` не запускает сборку Pages при push.
- Для уже настроенного Pages оставьте публикацию из `main:/docs`.
  Установка Updater не требует изменения Pages.
- При изменении `main`, пакета, снимков или плана требуется повторная проверка; автоматический режим формирует preview внутри того же запуска.
  Ошибка в любом событии, конфликт хеша, повтор уже зарегистрированного
  события или отказ тестов останавливают весь пакет до push.
  Успешный повторный запуск уже применённого пакета блокируется как дубль.
