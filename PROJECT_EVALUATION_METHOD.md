# Практическая приоритизация — пересмотр 4 ноября 2026

## Для кого и для чего

Основная цель — помочь исследователю выбрать небольшую практическую пробу под
конкретную задачу. Интерес для разработки платформы и мониторинга технологий
показывается отдельно. Нельзя объединять приложение, библиотеку, набор данных,
спецификацию и архивный сервис в один рейтинг качества.

## Градации при новой оценке

| Приоритет | Практическое решение | Обязательные основания |
|---|---|---|
| P1 | Кандидат на первую небольшую пробу | Задача и роль определены; география/формат подходят; понятны вход, результат и условия доступа; есть первоисточники конкретной версии, ограничения и план пилота |
| P2 | Сначала подготовить условия | Сценарий есть; явно названы настройка, разметка, адаптация или ограничение и проверяемый следующий шаг |
| P3 | Наблюдать за развитием | Для выбранной задачи пилот пока не обоснован или нужная функция остаётся планом; указано событие для пересмотра |
| Не оценён | Сначала уточнить сведения | Недостаток данных не заменяется нулём, P2 или низкой полезностью |

P1 не означает «готово к эксплуатации». Узкая страна, отсутствие русских данных,
роль стандарта или библиотеки сами по себе не понижают приоритет. Сначала выбираются
подходящие задача, роль, источники и формат; затем оценивается реалистичность пробы.
Трудность интеграции, зрелость и доказательность не складываются в общий балл.
Неизвестные значения остаются неизвестными.

Для готового приложения пилот — реальная пользовательская операция; для библиотеки —
небольшая интеграция; для стандарта — проверка модели/валидности/совместимости;
для набора данных — изучение покрытия, прав и качества эталона. Стандарт не получает
P3 лишь потому, что его нельзя запустить как программу.

## Порядок переоценки

1. Проверить адрес и тип записи. 404 и профиль владельца — отдельные проблемы ссылок,
   а не «плохо изученные характеристики». Не заменять URL предположением.
2. Определить задачу, роль, географию/язык/период/формат, вход и ожидаемый результат.
3. Сверить версию, документацию, доступ, лицензионные условия, необходимые данные
   и зависимости. Авторские показатели отделить от воспроизведённых результатов.
4. Сравнить с уже используемым способом и описать ограниченный пилот с критерием успеха.
5. Подготовить предложение P1/P2/P3 с источниками и ограничениями. До утверждения
   не подменять прежнюю оценку и сохранять её происхождение.
6. После утверждения синхронизировать данные и проверить сохранность старых сведений.

## Что означает нынешняя ведомость

Сохранённые A/B/C и P1/P2/P3 не переклассифицированы автоматически по новой модели.
Поле evaluation отделяется от более поздних проверок Watch. Если после даты оценки
источники проверяли снова, требуется сопоставление; E0 не повышается до E2 автоматически.
Триаж, неутверждённое предложение, отсутствие оценки и утверждение — разные состояния.
E2 без конкретной версии требует уточнения. Тесты самого каталога не являются E3
для перечисленных проектов. Ни одна новая числовая оценка этим пересмотром не присвоена.

# Методика оценки Genealogy Tech Watch — редакция 2026-10-28

## Назначение

Приоритет проекта показывает **ожидаемую практическую ценность для российского генеалогического исследовательского кабинета**, а не популярность GitHub, качество кода, активность автора или достоверность README. Сравнивать проекты следует по задаче и роли (готовое приложение, библиотека, стандарт, исследовательский прототип, архивный сервис), а не одним общим рейтингом.

## Раздельные оси

| Ось | Шкала | Критерий |
|---|---|---|
| Применимость к компонентам | 0–4 | 0 — нет выявленного сценария; 1 — косвенная идея; 2 — конкретный вспомогательный сценарий; 3 — полезный компонент; 4 — закрывает критическую потребность |
| Применимость к России | 0–4 / НД | 0 — несовместимо с задачей; 1 — нужна значительная адаптация; 2 — вероятно применимо после настройки; 3 — есть релевантные русские/российские сценарии; 4 — испытано на российских данных |
| Готовность к использованию | 0–4 / НД | 0 — идея; 1 — прототип; 2 — рабочий код без подтверждённой эксплуатационной устойчивости; 3 — тесты, релизы и документация; 4 — подтверждённая эксплуатация/совместимость |
| Качество свидетельств | E0–E4 | E0 — утверждение без проверяемого источника; E1 — README автора; E2 — код/документация/лицензия проверены; E3 — воспроизведён локальный тест; E4 — независимый benchmark на релевантном корпусе |
| Лицензия и данные | L0–L3 / НД | L0 — лицензия неизвестна или несовместима; L1 — ограничения требуют анализа; L2 — лицензия известна, но зависимости/веса/данные ещё не проверены; L3 — совместимость целевого сценария подтверждена |
| Интеграционная сложность | 0–3 / НД | 0 — самостоятельный инструмент или простой адаптер; 1 — ограниченная интеграция; 2 — отдельный сервис/пайплайн; 3 — существенная переделка архитектуры |

**НД** означает «нет достаточных сведений», а не ноль. Для E3/E4 обязательно фиксировать среду, входные данные, методику, результаты и ссылку на отчёт.

## Редакционный приоритет

- **P1 — изучить в первую очередь:** важный сценарий, реалистичный путь к пилоту или принципиально значимая архитектура. P1 допускается для экспериментальных решений, но рядом обязательно показывать E-уровень и зрелость.
- **P2 — наблюдать и проверять по задаче:** полезное, но не первоочередное решение, нишевая технология или заметные интеграционные издержки.
- **P3 — справочный/низкая текущая применимость:** ценность для задач кабинета ограничена; не означает плохое качество проекта.
- **Не оценён:** недостаточно оснований для приоритета. Не переводить автоматически в P2.

Приоритет назначается по обоснованию с компонентом, конкретным российским сценарием, ожидаемым результатом и сравнением с уже используемым решением. Никаких автоматических «баллов» по звёздам, количеству коммитов или размеру README.

## Обязательные поля оценки

`reviewed_at`, `reviewer`, `review_scope`, `source_urls`, `component_fit`, `russia_fit`, `maturity`, `evidence_level`, `license_risk`, `integration_effort`, `priority`, `priority_rationale`, `next_action`, `recheck_trigger`. Отсутствующие данные отмечать НД, не придумывать.

## Порядок аудита

1. Проверить существование и канонический URL, убрать дубли и ошибочные разделы.
2. Сверить README, LICENSE, релизы, коммиты и документацию с карточкой; датировать каждый факт.
3. Проверить поддержку России и русских исторических источников отдельно от общего описания.
4. Сопоставить с аналогами по компоненту; сформулировать проверяемый пилот.
5. Присвоить оси E/L/зрелости и только после этого подтвердить или изменить P1–P3.
6. Обновлять карточку, расширенное исследование, журнал и HTML seed только согласованно через существующий pipeline; до утверждения не подменять исходные оценки.
